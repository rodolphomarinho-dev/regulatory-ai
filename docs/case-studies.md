# From regulatory work to working systems

## 1. Audit preparation: better challenges, before the audit

**Problem.** Experienced auditors do not need a generic checklist. They need a focused view of the tensions between the plan, corrective actions, product context and supporting evidence.

**My contribution.** Develop scoped intake, functional focus, simulation roles and an evidence-linked challenge package. Keep source extraction, challenge and verification separate. Design reviewer handoffs and reusable project isolation.

**Output.** A challenge register, a concise review brief and an expert walkthrough. The intended benefit is focused preparation and a learning cycle across audits; measured time savings are not claimed here.

**Stage.** Toolkit built and technically checked with synthetic examples; broader audit effectiveness needs pilot evidence.

**What I would measure.** Preparation time including expert review; supported and useful challenges; unsupported findings; material issues missed; traceability; reviewer acceptance. Compare matched cases and document scope and reviewer differences.

**Public demo.** A fictional closed CAPA has missing, conflicting or corroborating effectiveness evidence. It demonstrates that a packet gap is not proof of real-world noncompliance.

## 2. Submission rehearsal: find the weak argument

**Problem.** A plausible simulation is not enough. The preparation must use the right product context, source material and expert questions. Early user feedback showed that the service model matters as much as the prompt.

**My contribution.** Design separate simulation modes and evidence contracts, then shape an expert-led preparation workflow: data cleanup, SME discussion, simulation and a review package. Historical feedback supplies context, not a shortcut to a predicted decision.

**Output.** Bounded questions and evidence gaps for the submission team to investigate. Pre-Submission discussion and submission challenge review remain distinct.

**Stage.** Prototype and technical checks; retrospective effectiveness evaluation remains to be demonstrated.

**What I would measure.** Freeze source availability at a defined date. Withhold the actual authority response from the simulation. Have independent SMEs score useful challenges, unsupported claims and material omissions. Check leakage from historical material and report uncertainty and repeated-run variation. An authority response is a useful comparator, not an exhaustive ground truth for every possible issue.

**Public demo.** A fictional assay claim covers two specimen matrices. The packet either supports both or only one. Changing the simulation's intended use changes its output contract.

## 3. Regulatory data: make feedback useful beyond one case

**Problem.** Health Authority questions in documents are hard to compare, link and reuse. A dashboard can make inconsistent definitions look more authoritative without making them correct.

**My contribution.** Build and run a bounded structured-feedback loading pilot; develop trend-report workflows; work across Regulatory, Data and IT on definitions and traceability. Preserve source wording and record relationships before adding interpretation.

**Output.** Reconciled pilot records, reusable feedback structures and a governed integration direction involving RIMS, Snowflake and Tableau.

**Stage.** Loading pilot delivered. Wider analytics and integration have separate ownership, access and release work; this portfolio does not claim a completed enterprise platform.

**What I would measure.** Extraction fidelity, correct parent-record links, duplicate handling, missing-answer handling and traceability. For trends, test dictionary consistency, denominator choice and whether reviewers can reproduce the interpretation from the cited sources.

**Public demo.** Inspect an orchestration layer that blocks specialist execution when a required source is missing or versions conflict, then routes a valid packet to human review without auto-authorizing release.

## Leadership through delivery

Across these examples, the work is not just model selection. It is agreeing the intended use, ownership and practical service; turning domain knowledge into a context and tool design; and giving colleagues a usable result. Data quality, eval design and change adoption belong in the same conversation.

All public examples are synthetic reconstructions. Project descriptions identify stage and contribution rather than claiming employer endorsement, validated regulatory effectiveness or production deployment.
